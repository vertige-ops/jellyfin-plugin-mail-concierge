# Security model

How Mail Concierge protects recovery, invitations and e-mail changes, and what it does not protect. To report a vulnerability, see [SECURITY.md](../SECURITY.md); the project overview is in the [README](../README.md).

## Design

- **Anti-enumeration**: the forgot-password API answers identically, with the same shape and timing, whether the account exists or has an address. Mails are sent in the background.
- **Limits** (defaults): 3 recovery e-mails per account and hour; 5 forgot-password requests per IP (IPv6 grouped by /64) per 15 minutes; separate server-wide budgets of 10 recovery, 10 invitation and 10 account e-mails per hour, so anonymous requests cannot starve invitations; a PIN is invalidated after 5 failures; an IP is blocked temporarily after too many failures.
- **Tokens** (invitation, reset, confirmation): long, random, single-use, expiring, stored only as hashes and compared in constant time. Opening a link (GET) only shows the page; the token is consumed by the form (POST), which resists mail scanners that open links.
- **E-mail change**: needs the current password; the new address is active only after confirmation; the old address gets a warning with a cancel link, valid 24 hours by default (`Validity of the cancel link`, in hours). A confirmed change invalidates pending resets.
- **Profile picture**: the browser shrinks it to 256 px; the server also reads the PNG, JPEG or WebP header (without decoding) and refuses images over 1024 px on a side, animated or malformed ones. The file is stored as sent, not re-encoded.
- **Public pages** share Jellyfin's origin, so they escape everything, use a strict CSP with a nonce and `Referrer-Policy: no-referrer`, and never insert administrator-provided HTML as is.
- Events are logged without any secret.

## Known limits and caveats

- `index.html` is served **uncompressed** while Mail Concierge is enabled, because the client script is injected into it.
- Jellyfin **locks an account after several wrong passwords**. This applies to the current-password check of the e-mail change form. An account that Jellyfin has locked this way (disabled after too many wrong passwords) **cannot use recovery**: an administrator must re-enable it first.
- **Trade-off of the cancel link**: it is sent to the *old* address, which may be the very mailbox the user abandoned because it was no longer trustworthy. To keep it from becoming an account takeover, cancelling also requires the account password (wrong passwords share the limit below), the link is short-lived, the address that gets replaced is notified, and the sessions of the account are closed according to the session policy of the settings. Anyone who knows the password can still cancel from the old mailbox; shorten the validity if that is a concern.
- To stay below that threshold, Mail Concierge accepts **at most 2 wrong passwords per hour and per user** in its forms (e-mail change, and the cancel page of an e-mail change); further attempts are refused without reaching Jellyfin until the hour is over. If the account was nevertheless locked by Jellyfin (several wrong passwords typed elsewhere), an administrator re-enables it in the Jellyfin dashboard (Users, the account, untick "Disable this user") and the user can try again.
- The links in e-mails carry their token in the URL. Jellyfin's **slow-request warning** can log the full URL of a slow request, so a token may appear in the Jellyfin log. Tokens are single-use and expire, but protect your logs.
- The generic Jellyfin plugin-configuration API still **exposes the SMTP and Seerr secrets to administrators**. Mail Concierge's own settings page never sends them back, but an administrator can read them through the generic endpoint. Administrators are trusted.
- **Recovery can be made unavailable by an anonymous attacker who knows a user name.** Requesting a code invalidates the previous code and link of that account, and the hourly recovery budget is shared by the whole server: a few requests can keep a user or, with several guessed names, everybody from getting a recovery e-mail for the rest of the hour. This is a nuisance, not an account takeover. Hidden accounts and unguessable names are not affected; lowering the per-address limits helps.
- **Reset and invitation tokens travel in the URL** of the public pages (the reset session in the query string, tokens in the link). Besides the Jellyfin slow-request log mentioned above, the logs of your reverse proxy and the browser history can keep them. Tokens are single-use or short-lived (a reset session lasts 10 minutes). Moving them out of the URL is planned.
- **Behind Docker's userland proxy**, every client can look like a private address; a client that sends an `X-Forwarded-For` header can then trip the proxy guard (see the last items below) for 15 minutes at a time. Run Jellyfin with host networking or put a real reverse proxy in front of it and list it in **Known Proxies**.
- **Stored data**: invitations (with the invited address) and unconfirmed addresses stay in `mailconcierge.json` until they are cleaned up when an administrator opens the invitation list; uninstalling the plugin leaves the file in the plugin data folder, and an address already copied to Seerr stays there. Delete these by hand if you need to.
- A LAN client sending a forged `X-Forwarded-For` can trip the proxy guard until **Known Proxies** is set, or until 15 minutes pass without another such request.
- **The logo in e-mails is loaded from your server.** Each HTML e-mail shows the logo through an image link built from the public URL (`.../MailConcierge/assets/logo.png`). When a recipient's mail client loads images, your server receives a plain request for that fixed file, with no token, address or other data of the recipient in it; it appears in the web server logs like any other request. Mail clients that block remote images simply show no logo. Without a valid public URL the logo is left out. The text version of every e-mail has no image.
- **Native TV and Swiftfin clients** do not load the web script. Their e-mail field and PIN screen are not available: entering a PIN there fails safely (it never becomes a password). Users should use the link in the e-mail.
